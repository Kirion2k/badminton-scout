## What the pipeline guarantees
**A forecast must be issued before its fixture's cutoff:**
- with a start time: 30 minutes before the start;
- with a date only: local midnight in the venue's timezone, so a far-east day that has already
  begun is closed.

**The fixture must:**
- have been checked within the last 24 hours (never in the future);
- be scheduled;
- not be listed twice.

**The players** must be linked by a person to established, connected BWF players.

**The ratings must be current:** no BWF import after the served run.

**What is stored:** the database clock time, the fixture revision and the cutoff. A trigger
forbids any change or delete.

**Outcomes** are recomputed from the fixture's verified state:

| State | Outcome |
|---|---|
| Completed | scored |
| Walkover, retirement, abandonment or cancellation | void |
| Start corrected to before the forecast | void |
| Player replaced, or a link undone | void |
| Verified result later changed | conflict, reported |
| Anything else | pending |

Every count is reported.

## Verification
- **Tests:** backend 575 passed (ruff, pyright strict). They cover every case in the brief, each
  on synthetic data:
  - a forecast before the start;
  - a start moved earlier, or later;
  - a postponement;
  - a replaced player;
  - a corrected time;
  - a result counted only once verified, never by the person who typed it;
  - a duplicate fixture, and clearing it by cancelling;
  - a same-name player never linked automatically;
  - irregular endings;
  - a link undone after the forecast;
  - a provider outage and an exhausted budget;
  - a stale rating snapshot;
  - stale, older and future readings;
  - immutability;
  - a reproducible evaluation;
  - credentials read only from the environment.
- **Web:** 22 tests passed. **Playwright:** 39 passed, 1 skipped.
- **Dry run on the development database:** synthetic future fixtures linked to two real rated
  players went through import → refused (unresolved) → link → forecast → result → self-check
  refused → verified → scored. It was rolled back, and the database was afterwards checked to
  have 0 fixtures, 0 forecasts and 0 events.
- **CI:** still blocked by the GitHub billing lock (`docs/ci-status.md`). These are local results.

## Independent review (10 findings)
- **Fixed:**
  1. **Duplicate flags never cleared.** Duplicates are now checked live, ignoring cancelled
     rows.
  2. **Older readings overwrote newer ones.** They are now ignored.
  3. **The four-eyes check named the importer.** It now names the CSV's `entered_by`.
  4. **Re-imports logged refusals again,** with categories split by timestamps. They no longer
     do.
  5. **A future `checked_at` disabled the staleness check.** It is now rejected.
  6. **Offsets in start times were dropped.** They are now rejected.
  7. **The fixture link accepted any source player.** It is now restricted to fixture sources.
  8. **Reconcile scanned every forecast.** It now scans only verified fixtures.
  9. **The identity lookup was duplicated.** It now reuses identity's lookup.
- **Documented, not changed:**
  - The downgrade fails while `bwf_curated` data exists, as 0022's does. It runs in one
    transaction, so nothing is left half done.
  - Operator names come from the OS user and the CSV, so the four-eyes check prevents mistakes,
    not deliberate fraud by a trusted operator (ADR-0014).
