# M8.1: BWF singles calibration, prospective evaluation and Mynton Matchup

2026-11-15. Protocol: ADR-0013, committed (`4099732`) before any calibration was fitted.
Results: `m8.1-calibration.json`, `m8.1-data-quality.json`, `m8.1-recompute.json`.
The M8 result files are unchanged.

## Summary

- **Recalibration is not supported by the development data.**
  - On 2012–2024 the frozen Glicko-2 model is slightly *under*-confident, not over-confident.
  - Neither calibrator improves held-out log loss, so the pre-registered rule keeps it
    uncalibrated.
  - The over-confidence seen in 2025–2026 is not a stable property of the model, and no
    historical fit can establish its fix.
- **Prospective evaluation is the only route to release.** It is built: forecasts recorded
  before matches, immutable, scored against verified results. But there is no authorised source
  of new BWF results today (the archive ends 2026-07-05), so **no forecast can be resolved yet**.
- **Mynton Matchup works with both public flags off.**
  - `GET /v1/matchups/compare` returns its five outcomes from real data.
  - `/compare` compares results, and never shows a percentage or a rating.

## 1. Historical test reuse

- **What happened:** the 2025-01-01 → 2026-07-05 BWF period was read twice in M8: the original
  evaluation, then a re-evaluation after the review fixes.
- **What follows:**
  - It is used here only as **"previously examined: diagnostic only"**.
  - Nothing in M8.1 was chosen or fitted on it.
  - The Glicko-2 configuration (τ 1.2, 3-day periods, RD₀ 250) is frozen at the M8 selection.
  - The fitter refuses any forecast after 2024-12-31: a code guard, plus a test.

## 2. Calibration (development 2012–2024, 30,100 forecasts)

All candidates work on the log-odds with no intercept, so P(A beats B) + P(B beats A) = 1 exactly,
and the order of the two players never matters.

|---|---|---|

| Experience-dependent temperature | 0.5330 | established 0.89–0.93, provisional 0.77–0.85 |

**Paired fold differences** (cluster bootstrap):

| Comparison | Difference (95% interval) |

  `30e6476d32c218a5`).

## 3. Prospective evaluation (built; nothing to resolve yet)

**`issued_prediction`** stores, for each forecast:
- issue time, scheduled date, external match reference;
- players, discipline, probability;
- configuration hash, calibration hash, run, snapshot and snapshot hash.

**Immutability:** a database trigger forbids deleting a forecast or changing anything forecast,
and allows the result to be set exactly once. A test checks each case.

**Commands:**

| Command | What it does |
|---|---|
| `scout matchups issue --a --b --discipline --on --ref` | Records a forecast. Refuses unless the route's own rules allow a probability (established, connected, not identity-flagged, rated) and the match is after the ratings' last day. |
| `scout matchups resolve --verified-by` | Matches open forecasts to imported results from the authorised BWF source only: same players, discipline, ±3 days, completed. Zero or several candidates leave a forecast open. |
| `scout matchups score` | Log loss and ECE with intervals, reliability, and the win-rate baseline on the same matches. |

**Release conditions (ADR-0013),** all required:
1. ≥ 1,000 resolved forecasts. That gives a log-loss interval of about ±0.02; M8's n = 4,313 gave
   ±0.016.
2. Beats the win rate, with a 95% interval below 0.
3. ECE's 95% upper bound is ≤ 0.04.
4. Every bin with ≥ 200 forecasts holds its observed rate in its 95% interval.
5. Independent review and owner approval.

**The honest constraint:**
- **The source:** BWF singles produces roughly 3,000 eligible matches a year (2025: 3,011 scored),
  but Mynton has no authorised feed of new BWF results. The BWF API is behind a challenge, and the
  compilation's next version is unknown.
- **The need:** a new results source, or an updated compilation version. Then forecasts issued
  before each tournament, and about 4 months of the circuit at that rate, reach condition 1.
- **Until then:** `PUBLIC_PROBABILITIES` stays `False` and `RELEASE_EVIDENCE` is `None`. With
  that, the code cannot produce a public probability even if the flag were turned on.

## 4. Mynton Matchup

**Route:** `GET /v1/matchups/compare?a&b&discipline=MS|WS`, checked against real data.

| Outcome | Example pair |
|---|---|
| comparison | Two established BWF men: "Mynton does not publish win probabilities yet". Head-to-head mirrors when the players are swapped. |
| comparison | A provisional player (< 10 BWF matches) |
| identity_uncertain | A player flagged by the BWF audit (5 of 4,836) |
| incompatible_pools | Unconnected BWF players; a BWF vs a federation player |
| comparison | Two federation adults, or a junior: results only, "no validated rating" |
| insufficient_data | A men's singles player asked for women's singles |
| 308 / 404 / 422 | Merged ids / withheld or unknown players / the same player twice |

**Flags:**
- `PUBLIC_PROBABILITIES` and `PUBLIC_RATINGS` are code constants, both `False`.
- Ratings appear only with `PUBLIC_RATINGS`, and only for BWF singles.
- Anything rating-derived is sent `no-store`.

**Served ratings:**
- `scout ratings serve-bwf` runs a full rebuild of a fresh BWF snapshot. Its hash is identical to
  M8's snapshot 1: the archive has not changed.
- Ratings are stored per player with component and identity flag. Only `bwf:MS` and `bwf:WS` are
  ever written or read.

**Page `/compare`:**
- Two-player search (works without JavaScript) and a men's or women's singles choice.
- Content: the matchup status in words, meetings, recent results, common opponents, data
  freshness and limitations.
- Desktop and mobile screenshots: no overflow, no percentage anywhere.
- Axe and overflow checks in the Playwright suite.

## 5. Junior privacy

- **No route serves a rating except the gated matchup.** A test reads the whole API schema: rating,
  deviation and probability fields exist only in the matchup evidence.
- **The matchup never reads a federation or junior pool.** Juniors and federation players get
  results-only outcomes, never rating fields, even with both flags on (tested).
- **No rating-derived metadata:** page titles are fixed.
- **Offline junior and federation ratings** live only in local derived tables, read by offline
  commands.

## 6. Data quality

- **Category.** "Adult" now needs a recognised discipline and a tournament that is not mostly
  (≥ 80%) junior; otherwise the category is unknown and excluded from pools.
  - About 26,000 federation matches moved from adult to unknown. Nearly all already lacked a
    discipline.
  - Singles matches without a category in the rating pools: 416 (snapshot 5).
- **GD/MD regression audit:** for each source and doubles discipline, sides are checked against
  the gender implied by players' singles.
  - German and Flemish GD/MD: 0% contradictions.
  - Highest anywhere: 1.2% (mixed doubles, global source).
- **The side-1 effect is seeding:**
  - federation listings put the seeded player first 2.5 times as often (32,309 vs 13,025
    matches);
  - a seeded side 1 wins 78.6%;
  - with neither seeded, side 1 wins 51.3%.
  - Seeding is genuine pre-match information. Per instructions it is **not** a model input.
- **Identity resolution:** unchanged.

## 7. Verification

- **Formula check:** 500 sampled pairs agree with a separately written Glickman expectation to
  1e-16, and P(A,B) + P(B,A) − 1 ≤ 2e-16.
- **Rebuild reproducibility:** a second rebuild reproduces all 4,836 ratings identically.
- **Predictions match the backtest:** the production run's 48,607 predictions equal M8's backtest

## 8. Remaining limitations

- **No new BWF data source,** so prospective evidence cannot accumulate. This blocks release.
- **The archive is static.** "Data as of 2026-07-05" will age. Ratings of players inactive since
  then become less informative.
- **BWF identities are names:** 5 flagged; same-person spellings are undetectable.
- **Federations remain disconnected islands.** Their probabilities are out of scope (owner
  decision).
- **Calibration may drift.** The temperature drift over 2016–2024 implies any future calibration
  must be re-checked on prospective data, not assumed stable.

## 9. Independent review (10 findings, all confirmed and fixed)

**The prospective evidence:**
- **Forecasts for played matches.** Forecasts were accepted for matches already played. Now:
  - a forecast must be for a match after today;
  - a result counts only if played on or after the issue day.
- **Duplicate forecasts.** The same match could be forecast twice and counted twice. Now there is
  one forecast per match: a unique index over the players in either order, discipline and day,
  plus a check before issuing.
- **Stale uncertainty.** Probabilities ignored inactivity since the archive ended, which made them
  over-confident for later matches. Each deviation now grows per idle rating period up to the
  match date, as in the backtest. Tested: later matches give less confident forecasts.

**The probability path** (unreachable today):
- **Crashes.** It would have crashed on empty bins and on the shape of the evaluation's log loss.
- **Track record.** The track record is now from the favourite's side: the same whichever player
  is A, and worded correctly. A forecast outside every validated bin gets no number.

**Identity:**
- **Merges after the rebuild.** A merge after the ratings were built could attach a rating to the
  wrong person. Such a pair is now `identity_uncertain` until the next rebuild. Tested.

**The page:**
- **Redirects.** A merged id raced two redirects, and could leave `/compare` or lose the
  discipline. The matchup is fetched first, and a merged first player resolves in place. Tested
  end to end.
- **Text and markup.** The data date now comes from the API (no hard-coded "July 2026"), and the
  markup is valid.

**Engineering:**
- **Duplicated logic.** `Served` building was duplicated, and the established threshold was
  defined three times. Both now have one definition.
- **Repeated work.** The merge map was recomputed per forecast; it is now computed once.
- **Missing tests.** The audits and the rebuild bookkeeping had no tests; now they do.
- **Fold guard.** The fold loop skips an empty year instead of dividing by zero.

**After the fixes:**
- backend 556 passed (ruff, pyright strict);
- web 22;
- Playwright 39 passed, 1 skipped.
